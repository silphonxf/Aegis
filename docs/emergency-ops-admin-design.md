# 运维工具管理端（Admin Console）V2.0 重构设计文档

> 文档目标：将 Aegis 管理端从“按技术模块堆页面”的联调后台，重构为“围绕运维业务闭环”的正式管理控制台。新版重点解决菜单分散、配置项过底层、资产/系统/人员脱节、应急动作碎片化等问题。

---

## 1. 核心设计理念与目标

### 1.1 化繁为简
废除复杂的技术底层表单（如 JSON 参数、`action_code`、大量手工输入框），优先采用：

- 向导式配置
- 下拉联动
- 多选绑定
- 模板化脚本录入
- 默认值与预置项

目标是让管理端从“技术人员配置台”转成“运维人员可直接使用的业务后台”，预计精简 70% 左右的无效输入项。

### 1.2 业务闭环
将原本离散的：

- 硬件资产
- 信息化系统
- 巡检记录
- 自检记录
- 应急动作
- 人员角色

统一串成闭环，实现：

**基础数据录入 → 系统/机房配置 → 日常巡检/自检 → 异常发现 → 一键预案处置 → 审批与审计留痕**

### 1.3 权限隔离
引入极简 RBAC：

- 普通管理员（User）：只看自己负责的系统和关联预案
- 超级管理员（Admin）：拥有全局视角，支持全局配置、审批、交接与审计

### 1.4 拒绝手打，强化联动
整体设计遵循：

- 数据字段精简
- 拒绝重复手打
- 全靠联动选择
- 一处录入，多处复用

### 1.5 安全可审计
所有高风险动作必须具备：

- 明确触发来源
- 审批或确认卡点
- 完整审计日志
- 风险等级标识
- 可追溯的证据链/快照

---

## 2. 总体重构目标

当前管理端更偏“联调后台”，菜单按技术能力散落，用户需要理解过多底层概念。V2.0 的目标是把它收敛为 **4 大核心模块**，以业务流程替代技术分类。

### 2.1 重构后的四大核心模块

1. **监控大盘（Dashboard）**
2. **资产与日常运维**
3. **应急预案配置（Runbook）**
4. **运维审批与审计**

### 2.2 菜单收敛原则

弃用原有 8+ 冗余菜单，将零散页面归并为高内聚导航：

| 原分散能力 | 新归属模块 |
|---|---|
| 系统管理 / 用户管理 / 模板管理 / 巡检配置 / 基础 IP 录入 | 资产与日常运维 |
| SSH 主机配置 / 服务器动作 / 数据库动作 / 进程动作 | 应急预案配置 |
| 工具任务审批 / 审计日志 / 高危执行审批 | 运维审批与审计 |
| 监控总览 / 全局状态 | 监控大盘 |

## 3. 信息架构设计

## 3.1 监控大盘（Dashboard）

### 定位
作为首屏总览入口，保持现有“全局状态展示”定位，但未来要更突出：

- 当前异常系统数
- 未填报自检数
- 未完成巡检数
- 最近 24 小时高风险动作数
- 最近待审批事项数

### 建议展示内容

- 系统状态 KPI：绿色 / 黄色 / 红色 / 总系统
- 核心资源指标：CPU / MEM / DISK
- 异常系统列表
- 今日自检填报概览
- 今日巡检完成概览
- 待审批事项概览
- 最近高风险操作摘要

### 设计原则

- 首屏只放“看板与跳转入口”
- 详情下钻进入其他模块
- 异常项必须高亮且支持一跳联动

## 3.2 资产与日常运维

这是新版管理端的核心模块，采用 **三页签（Tab）结构**，解决系统、机房、人员、基础数据分裂的问题。

### Tab 1：系统自检配置与记录

#### 设计目标
建立：

**系统 → 运行服务器 → 自检负责人 → 自检记录 → 异常联动预案**

让“谁负责哪个系统、系统最近是否自检、异常后能否处置”在一个页面里形成闭环。

#### 页面布局建议

- **左侧：系统与负责人配置区**
- **右侧：系统自检记录区（近 30 天）**

#### 左侧配置区字段

- 系统名称
- 运行服务器 IP / 服务器组
- 自检负责人（支持多选）
- 检查频次（每班次 / 每日 / 每周 / 自定义）
- 最新状态（正常 / 异常 / 未填报）
- 最近填报时间
- 操作（详情 / 编辑 / 一键处置 / 提醒）

#### 新建系统弹窗
只保留核心字段：

- 系统名称（必填）
- 运行服务器（下拉选择，支持单选/多选）
- 自检负责人（下拉多选，来源于用户列表）
- 检查频次（下拉）
- 关联预案（可选）
- 备注（可选）

#### 右侧记录区建议字段

- 填报时间
- 系统名称
- 填报人
- 状态
- 异常说明
- 是否已触发预案
- 操作（查看详情 / 查看联动记录）

#### 关键联动能力

1. 自检负责人来源于基础用户数据
2. 运行服务器来源于基础 IP/服务器数据
3. 系统异常时支持一键跳转到 Runbook
4. 支持多负责人，满足多班次交接
5. 支持按状态筛选：全部 / 正常 / 异常 / 未填报

---

### Tab 2：机房巡检配置与记录

#### 设计目标
建立：

**机房物理位置 → 唯一二维码 → 巡检记录 → 异常备注 → 后续追踪**

重点强化线下巡检与线上配置之间的直接关联。

#### 页面布局建议

- **左侧：机房与二维码管理**
- **右侧：机房巡检历史记录**

#### 左侧管理区字段

- 机房/区域名称
- 物理位置描述
- 关联二维码 ID
- 最近巡检人
- 最近巡检结果
- 最近巡检时间
- 操作（生成二维码 / 下载二维码 / 编辑）

#### 核心能力

- 一键新增巡检机房
- 一键生成二维码
- 一键下载二维码
- 支持机房/区域的唯一编码管理
- 支持异常机房高亮显示

#### 右侧巡检记录区字段

- 巡检时间
- 机房名称
- 巡检人
- 巡检结果
- 备注
- 图片/附件（后续可扩展）
- 操作（查看详情）

#### 关键联动能力

1. 手机扫码结果必须能回溯到机房配置项
2. 异常巡检项应在右侧列表高亮
3. 可按巡检人 / 状态 / 时间范围筛选
4. 后续可与资产位置、告警记录联动

---

### Tab 3：基础数据录入

#### 设计目标
集中维护所有上层页面依赖的基础源数据，作为全局下拉数据源。

#### 子模块 A：用户管理

建议字段：

- 姓名
- 工号/账号
- 联系电话
- 系统角色
- 负责系统数量
- 状态
- 操作（编辑 / 重置密码 / 停用）

其中 **系统角色** 为关键字段，用于后续 RBAC 控制：

- 普通管理员（User）
- 超级管理员（Admin）

#### 子模块 B：服务器基础 IP 录入

建议字段：

- 服务器名称
- IP 地址
- 端口
- 所属系统（可选）
- 所在机房/区域（可选）
- 连接方式（SSH / DB / Agent）
- 备注

#### 批量导入要求

支持：

- Excel 模板下载
- Excel 批量导入
- 导入校验结果预览
- 成功/失败条目反馈

#### 关键联动能力

1. 用户数据作为系统负责人、自检负责人下拉源
2. IP/服务器数据作为系统运行服务器、预案目标服务器下拉源
3. 用户角色直接驱动权限显示范围

## 3.3 应急预案配置（Runbook）

此模块用于替代原先“SSH 配置 / 服务器动作 / 数据库动作 / 进程动作”分散式管理方式，统一升级为：

**预案脚本库（Runbook Library）**

### 设计目标

- 一切应急动作统一抽象为“预案”
- 配置尽量只保留业务层必要字段
- 底层 SSH 凭据与执行细节由后台封装处理
- 与系统自检异常联动

### 3.3.1 预案列表

建议字段：

- 预案名称
- 适用系统
- 目标执行服务器
- SSH 凭证关联
- 触发机制
- 最近执行时间
- 风险等级
- 操作（编辑代码 / 测试连接 / 启用停用）

### 3.3.2 新建/编辑预案表单

原则上只展示 3 个核心输入项：

1. **预案名称**
2. **适用系统**（下拉）
3. **执行脚本**（Shell / SQL）

可折叠展开的高级项：

- 目标执行服务器（默认可从系统绑定自动带出）
- 触发方式（手动 / 自检异常联动 / 需审批）
- 风险等级（低 / 中 / 高 / 极高）
- 超时设置
- 输出截断长度
- 备注

### 3.3.3 底层封装原则

- SSH 主机凭据不在前端大面积平铺
- 密码 / 私钥仅后台加密存储
- 前端编辑时不回显原始密钥
- 预案执行时由后台完成凭据解密与连接

### 3.3.4 联动处置

当系统自检报红时：

- 支持一键触发关联预案
- 对高风险预案自动进入审批流
- 执行结果自动写入执行日志和审计日志

### 3.3.5 预案执行历史

建议放在同模块右侧或下方联动展示：

- 执行时间
- 预案名称
- 触发源/操作人
- 目标 IP
- 最终结果
- 执行耗时
- 日志快照入口
- 审批链路入口

## 3.4 运维审批与审计

该模块是安全与合规的核心收口模块，统一承接：

- 高危动作审批
- 预案变更审批
- 高级工具执行审批
- 审计日志查询
- 证据链留痕

### 3.4.1 运维审批管理列表

建议字段：

- 申请时间
- 申请人
- 审批类型
- 关联对象/系统
- 申请原因
- 审批状态
- 操作（同意 / 驳回 / 查看详情）

#### 审批类型建议

- 高危脚本执行
- 预案脚本变更
- 高级工具执行
- 权限交接/负责人调整

### 3.4.2 操作审计日志看板

#### 核心目标
建立不可抵赖的全量留痕能力，至少覆盖四要素：

- 时间
- 人物
- 地点（客户端 IP / 终端）
- 行为

#### 建议字段

- 操作时间
- 操作账号（工号）
- 客户端 IP
- 业务模块
- 操作类型
- 操作行为详细描述
- 风险等级
- 快照/证据链

#### 风险等级建议

- 低风险 🔵
- 中风险 🟡
- 高风险 🟠
- 极高危 🔴

#### 快照/证据链示例

- 查看终端命令快照
- 查看前后代码 Diff
- 下载原始导入 Excel
- 查看执行输出摘要
- 查看审批意见

#### 交互增强建议

- 高风险 / 极高危记录整行浅红底高亮
- 操作账号支持跳转到用户详情
- 关联对象支持跳转到系统详情或预案编辑页
- 支持按风险等级、模块、时间范围筛选

## 4. 极简权限控制（RBAC）

## 4.1 角色定义

### 普通管理员（User）

登录后仅可见、可操作：

- 自己负责的系统
- 自己关联的自检记录
- 自己可触发的预案
- 自己提交或参与的审批事项

目标是：

- 避免信息过载
- 防止越权误操作
- 保证职责边界清晰

### 超级管理员（Admin）

拥有全局能力：

- 查看所有系统、自检、巡检、预案、审批、审计
- 配置基础数据
- 配置预案库
- 审批高危操作
- 跨系统调整负责人
- 快速交接权限范围

## 4.2 RBAC 在界面上的体现

| 能力 | User | Admin |
|---|---|---|
| 查看本人负责系统 | ✅ | ✅ |
| 查看全部系统 | ❌ | ✅ |
| 编辑基础数据 | ❌/受限 | ✅ |
| 编辑预案脚本 | 受限 | ✅ |
| 执行高危预案 | 需审批 | ✅/可审批 |
| 查看全量审计 | ❌ | ✅ |
| 调整系统负责人 | ❌ | ✅ |

## 4.3 秒级交接

Admin 应支持在界面上快速完成：

- 系统负责人变更
- 多负责人增删
- 班次交接
- 临时接管

后续可扩展为拖拽式交接或批量分配。

## 7. 安全设计要点

### 7.1 敏感信息处理

- SSH 密码/私钥必须加密存储
- 主密钥仅放环境变量，不进仓库
- 前端不回显敏感原文
- 审计日志自动脱敏

### 7.2 高危动作卡点

以下操作建议进入审批或强确认：

- 执行高危预案
- 修改高危预案脚本
- 批量导入覆盖核心基础数据
- 调整系统负责人/权限范围
- 数据库高风险操作

### 7.3 审计防抵赖

所有关键动作必须记录：

- 谁发起
- 从哪发起
- 何时发起
- 作用于什么对象
- 改了什么 / 执行了什么
- 结果如何
- 证据链在哪里

## 8. 交互与视觉建议

### 8.1 状态标签规范

状态列统一使用 Badge/Tag 组件：

- 正常 🟢
- 异常 🔴
- 待审批 ⏳
- 已通过 ✅
- 已驳回 ❌
- 未填报 ⚪

### 8.2 风险高亮

审计日志中：

- **极高危 🔴**
- **高风险 🟠**

建议整行轻微泛红底，增强感知。

### 8.3 联动跳转

以下字段建议支持超链跳转：

- 审计日志中的操作账号 → 用户详情
- 审计日志中的关联对象/系统 → 系统详情
- 审计日志中的预案名称 → 预案编辑页
- 自检异常项 → 对应 Runbook
- 待审批项 → 对应审批详情

## 9. 实施建议（分阶段）

## 第一阶段：信息架构与界面重组

目标：先把管理端从“技术页集合”重组为新版四大模块。

建议工作：

- 调整左侧菜单结构
- 完成“资产与日常运维”三 Tab 页面骨架
- 完成“Runbook 脚本库”页面骨架
- 完成“审批与审计”页面骨架

## 第二阶段：基础数据联动

目标：让用户、系统、服务器、机房等基础数据真正互相驱动。

建议工作：

- 建立统一下拉源
- 支持负责人绑定
- 支持服务器绑定
- 支持二维码与巡检点绑定
- 支持 Excel 批量导入

## 第三阶段：应急联动与审批闭环

目标：把异常、自检、预案、审批、审计串起来。

建议工作：

- 自检报红后联动 Runbook
- 高危预案进入审批流
- 执行结果沉淀到审计日志
- 快照与证据链可回查

## 第四阶段：权限与交接优化

目标：把 Admin / User 两种角色体验彻底拉开。

建议工作：

- 基于负责人过滤数据
- 超级管理员全局视角
- 快速调整系统负责人
- 批量交接能力

---

## 10. 与当前 Aegis 现状的衔接建议

结合当前项目状态，建议这样落地：

1. **保留现有 Dashboard 能力**，只做信息聚合增强
2. **将现有用户管理 / 系统管理 / 模板管理 / 巡检相关能力**，重组到“资产与日常运维”
3. **将现有应急处置配置能力**，从“SSH/服务器/数据库/进程”页面模型，收敛到“Runbook 脚本库”模型
4. **将工具任务审批与审计日志能力**，整合到统一的“运维审批与审计”
5. **后端模型先允许兼容旧表结构**，前端先按新 IA（Information Architecture）组织页面，分阶段迁移数据模型

---

## 11. 一句话总结

Aegis 管理端 V2.0 不再是一个“技术配置台”，而要升级成一个：

**围绕系统、机房、人员、预案与审计构建的运维业务控制台。**

它的核心关键词不是“字段更多”，而是：

**更少输入、更强联动、更清晰权限、更完整闭环。**
